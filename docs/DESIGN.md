# 小秘书 · 设计文档

> 版本 v1.1 ｜ 2026-11-13 ｜ 对应实现：`task.py`（约 900 行）、飞书库「小秘书」
> v1.1 变更：系统更名「小秘书」；核心定位由单一机制调整为三重职责；重估本地归档产物（结论见 2.3）

---

## 1. 需求定义

### 1.1 要解决的问题

**核心定位：小秘书要同时承担三件事——推动每个任务走到闭环、把已完成的整理成可查阅的记录、给出一眼能看清的看板。**

三者缺一不可，且互为条件：

- **闭环**是目的。任务记下来不是为了"被记下来"，是为了被做完。清单类工具的死穴就在这里：录入时有热情，两周后变成一堆没人看的条目。
- **总结**是闭环的一部分。做完不等于结束——不留结论的完成，三个月后和没做过一样，"这个月干了什么"将无从回答。总结发生在 `done` 的那一刻，不靠事后回忆。
- **看板**是闭环的前提。看不清现状就不知道该推哪件，也就谈不上闭环。它同时回答"现在该做什么"和"最近都干了啥"。

由此拆出三个具体病灶，按严重程度排序：

| # | 病灶 | 具体表现 | 判定依据 |
|---|---|---|---|
| 1 | **做一半丢了** | 一件事开头了没结尾，第二次提起已经想不起上次做到哪 | 跨日任务重新开始时，需要重新回忆上下文 |
| 2 | **假完成** | 事情看起来结束了，实际只是把问题挪了个地方 | 发消息问别人被当成"完成"；需求没想清就说"先按这个做" |
| 3 | **无声腐烂** | 任务长期躺在列表里，既没推进也没被正式放弃 | 同一件事顺延三次以上，仍然出现在待办里 |

这三个病灶共同的特征是：**当事人自己不会主动发现**。所以系统必须承担"暴露"的职责，而不是等使用者自觉。闭环、总结、看板三件事，本质上分别对应"它替你管住终点、管住产出、管住视野"。

### 1.2 设计不变量

下面五条是硬约束。任何设计如果违反其中一条，即使功能更完整也必须推翻重做。这是过去四轮返工总结出来的。

**I1｜不得引入需要专门打开的新入口。**
理由：任何需要"先想起来去打开它"的工具，使用率会在两周内降到零。只能用已经每天在用的载体。

**I2｜一次调用取回全量，禁止递增式查询。**
理由：查询成本由"读多少个对象"决定。40 个任务如果分散在 40 个文件里，单次盘点要读 40 次；如果在一张表里，读 1 次。**成本相差 40 倍**，这个差距会直接决定 agent 愿不愿意频繁查询，进而决定系统是否被真正使用。

**I3｜写入必须经过统一入口，且校验发生在写入瞬间。**
理由：靠事后检查或者靠使用者自觉，一定会漏。状态字段写错一个值，看板就静默漏掉一条任务，而没人会发现。

**I4｜数据必须能脱离本机实时读取。**
理由：本机数据要靠 commit+push 才能到手机，中间有延迟；本机关机就断。任务管理恰恰是"人不在电脑前"时最需要的东西。

**I5｜记一件事的成本必须低于 30 秒。**
理由：录入摩擦是这个系统最大的敌人。字段填不全可以容忍，多花两分钟就会让人放弃记录。

### 1.3 明确排除

以下方案已经评估并否决，记录理由以防重走：

| 方案 | 否决理由 | 违反的不变量 |
|---|---|---|
| 自建网页 / 本地应用 | 换环境即丢失，且需要专门打开 | I1、I4 |
| 一个任务一个 Markdown 文件 | 盘点成本随任务数线性增长，40 个任务需 40 次读取 | I2 |
| 本地 Markdown 单表 + git | 手机端必须 commit+push 才有最新数据，关机即断 | I4 |
| 接入飞书/钉钉日历做日程源 | 真实日程不在该平台，接入了也读不到 | 实际无效 |
| 8 字段 frontmatter 强制填写 | 任务开始时"完成标准"多半是猜的，强制填写只会伪造 | I5 |
| 依赖"定时任务监控另一个会话" | 该机制不存在；定时任务各自独立运行，看不到其他会话 | 技术不可行 |

### 1.4 术语

| 术语 | 定义 |
|---|---|
| **任务** | 能用一句话描述、能用一句结论验收的最小工作单元 |
| **完成标准** | 一句可验收的话。写不出来说明这件事还没想清 |
| **真完成** | 达到了当初写下的完成标准 |
| **假完成** | 状态改成了已完成，但完成标准没达到，或只是把问题转移 |
| **推进** | 有实质进展但今天没到终点。**必须与完成区分**，否则会制造虚假的效率感 |
| **顺延** | 一件任务没有推进而被推迟。每次卡住累加 1 |
| **项目** | 需要多个任务才能验收的集合。本身不是任务 |
| **归档** | 完成或放弃的任务脱离活跃工作集，进入可长期查阅的历史。**实现方式是视图过滤**（终态记录仍在主表内，靠「归档月」字段被活跃视图排除），而非物理移出；月度台账 `ledger.md` 另存一份只追加的书面历史 |

## 2. 设计思路

### 2.1 存储位置：飞书多维表格

**决策：飞书多维表格做唯一主库。**

选型对照：

| 候选 | 满足 I1 | 满足 I2 | 满足 I3 | 满足 I4 |
|---|---|---|---|---|
| 本地 Markdown | ✅ 编辑器随手可开 | ❌ 需遍历文件 | ❌ 无校验层 | ❌ 需 push |
| 飞书日历 | ✅ 原生 App | ❌ 无状态字段，无法查询 | ❌ 事件无字段约束 | ✅ |
| **飞书多维表格** | ✅ 原生 App | ✅ 服务端过滤一次返回 | ✅ 字段类型即约束 | ✅ 零延迟 |

关键判断：**日历和表格不是同类替代品。**

- 日历是**时间块容器**，只有"时间 + 标题"，无法表达待做/进行中/完成/放弃，无法统计，无法放层级。
- 多维表格是**结构化数据表**，字段类型自带约束，支持服务端过滤、分组、聚合。

因此多维表格做主库，日历作为它的一个视图存在（同一份数据，多种呈现）。这样就同时得到了"日历视角"和"数据能力"，且不需要维护两份数据。

### 2.2 为什么要脚本

**决策：`task.py` 是唯一写入通道。**

这条不是为了"方便"，而是 I3 的落地方式。具体防的是三件事：

1. **枚举值漂移**：`doing` / `进行中` / `在做` 三种写法会让筛选静默失败。脚本做别名归一，飞书侧只存一种值。
2. **必填项缺失**：完成不写结论、卡住不写原因，脚本直接拒绝并返回非零退出码。
3. **ID 生成**：不靠人工维护计数器，由飞书 `auto_number` 字段自动生成。

代价要认：**脚本是单点，它坏了全都停。** 所以 `doctor` 子命令必须能一次性定位故障环节（6 项检查：CLI 可执行、授权有效、表可访问、归档目录存在、可写、git 已初始化）。

### 2.3 本地归档产物的去留（v1.1 重估）

**背景：** 最初的设计里，每次写操作会在本地生成三个产物——`DASHBOARD.md`（人看）、`data/tasks.json`（全量快照）、`archive/YYYY-MM/ledger.md`（月度台账）。既然飞书已是唯一主库且手机实时可读，这三个产物是否还有必要？逐个评估：

**逐项判断：**

| 产物 | 飞书侧能否替代 | 判断 | 理由 |
|---|---|---|---|
| `DASHBOARD.md` | 仪表盘 + 5 视图基本覆盖 | **保留但降级为可选** | 它的真实用户不是人，是 **agent**：WorkBuddy 会话里读一个本地文件，比调 lark-cli 拉全表再自己排版便宜一个数量级，且离线可读。人日常看飞书，agent 用这份。 |
| `data/tasks.json` | 结构化数据飞书全有 | **保留，但职责改名"快照"而非"恢复"** | 原设计标注"恢复用"是误导——恢复只需目录+授权，用不到它。真实价值：① 飞书整库不可用（误删库、账号问题）时的最后一份全量冷备；② 不经过 API 就能被 grep / diff 的明文。每次写操作自动更新，成本为零。 |
| `archive/…/ledger.md` | 可用"已完成"筛选视图替代 | **保留** | 月度台账是"按月翻旧账"的形态，飞书视图按月分组可以做到类似效果，但台账有两个不可替代点：① 只追加、进 git，天然带变更历史（谁在何时把结论改了，diff 可见）；② 不依赖飞书账号和 API，十年后任何编辑器都能打开。 |

**结论：三个都留，但理由和 v1.0 不同了。**

v1.0 的理由是"归档需要"，v1.1 的理由拆成三层：

1. **数据主权层**（tasks.json、ledger.md）：飞书是云服务，数据在别人手里。冷备+台账进 git，是"就算飞书没了也能完整带走"的保险。成本几乎为零（脚本顺带生成），收益是极端情况下的全部历史。
2. **agent 便利层**（DASHBOARD.md）：给 WorkBuddy 会话省一次全表 API 调用，也让"看板"这个职责在本地编辑器里有一个落点。
3. **人阅读层**：这层**飞书全权负责**，本地不再承担"给人看"的职责。手机看飞书，电脑也看飞书——DASHBOARD.md 如果哪天嫌乱，可以降级为只在 `sync` 时生成，不随每次写操作刷新。

**但要诚实：不删的前提是它们是自动派生的。** 一旦某个产物开始需要人工维护，就应该立刻删掉它——这与 I5（录入低于 30 秒）的精神一致：任何"需要人付出额外劳动才能维持"的产物都是负担，不是资产。

改动落实：
- `tasks.json` 的注释从"恢复用"改为"全量快照·冷备"，README 与 3.6 同步改
- 3.7 恢复方式中删去对 tasks.json 的暗示（原本也没明说，但避免误导）
- 新增飞书侧「⑤ 已完成归档」视图的计划（见 4.3），让"翻旧账"在飞书里也有直接入口

```
飞书主库  ──派生──►  DASHBOARD.md      （agent 看 + 离线可读）
          ──派生──►  data/tasks.json  （全量快照·冷备，防极端情况）
          ──派生──►  archive/YYYY-MM/ledger.md  （只追加台账，进 git）
三层互为冗余，任何一份丢失都能从主库重建，或从另两份交叉恢复。
```

### 2.4 三个职责如何落地

闭环、总结、看板三个职责不是三组功能，而是同一套字段和命令在不同环节的复用。**去掉任何一个，另外两个都会退化**：

**职责一：闭环——每个任务必须走到终点。**

- `done` 缺少 `--summary` 直接失败。针对"假完成"——人会下意识把"发出去了""问了别人"报成完成，因为心理负担最小。强制写一句结论，会让"其实还没结束"暴露出来。
- `block` / `drop` 缺少 `--reason` 失败，要求"具体到等谁、缺什么"，不接受"有点难"。放弃是有效决定，但必须留痕。
- `block` 每次让 `顺延次数 +1`，计数永久保留（完成时不清零），月度复盘才能看出"哪类事反复被推迟"。同优先级内顺延多的排前面——**让问题主动撞到使用者眼前，而不是等着被想起**。

**职责二：总结——结论沉淀在完成的瞬间。**

总结不靠事后回忆，靠 `done --summary` 那一句。它同时流向三处：飞书记录的「小结」字段（可查询）、月度台账 `ledger.md`（可回溯）、`notes/` 单件总结（可选深挖）。写的时候是一句话，一个月后它就是"这个月干了什么"的答案。

**职责三：看板——手机上一眼看清现状。**

飞书侧 5 个视图 + 仪表盘解决"随时看"，本地 `DASHBOARD.md` 解决"给 agent 和编辑器看"。看板不新增数据，全部从主库派生——它清楚了，就说明数据模型是通的；它糊了，问题一定在录入环节。

闭环失败的样子：列表越来越长，看板越来越糊，最后连记录本身都变成负担——这正是这套设计要避免的终局。

## 3. 具体实现

### 3.1 总体架构

```
      ┌────────────────────────────────────────────┐
      │  飞书 App（手机 / 网页）                     │
      │  ─ 5 个视图：表格·今日·看板·日历·甘特        │
      │  ─ 1 个仪表盘：4 指标卡 + 3 图表             │
      └───────────────┬────────────────────────────┘
                      │ 实时，无需同步
      ┌───────────────▼────────────────────────────┐
      │  飞书多维表格「小秘书」（唯一主库）             │
      │  base: <实例的 base_token，见数据仓 config.json>   │
      │  table: <实例的 table_id>（任务表，21 字段）        │
      └───────────────▲────────────────────────────┘
                      │ lark-cli（结构化 API）
      ┌───────────────┴────────────────────────────┐
      │  task.py  ← 唯一写入通道，负责校验与归一      │
      └───────────────┬────────────────────────────┘
                      │ 每次写操作后派生
      ┌───────────────▼────────────────────────────┐
      │  数据仓 xiaomishu-data/                     │
      │  ├ DASHBOARD.md        agent 看的看板          │
      │  ├ data/tasks.json     全量快照·冷备           │
      │  ├ archive/YYYY-MM/    月度台账（只追加）     │
      │  └ notes/YYYY/         单件总结              │
      └────────────────────────────────────────────┘
```

数据流方向是**单向的**：飞书 → 脚本 → 本地文件。本地文件永远不反向写回飞书。这样消除了双向同步的一致性问题。

### 3.2 数据模型

单表「任务」，21 个字段。设计原则是**字段尽可能少**（I5），且每个字段都有明确的写入方。

| 字段 | 类型 | 写入方 | 说明 |
|---|---|---|---|
| 任务ID | auto_number | 飞书自动 | 规则 `T-{创建日期}-{自增2位}`，如 `T-20261113-01`，不可手填 |
| 任务 | text | 用户 | 一句话说清做什么。要求一周后的自己能看懂 |
| 完成标准 | text | 用户（可空） | 可验收的一句话。**允许留空**，等任务被顺延过一次再补 |
| 状态 | select(单选) | 脚本 | 待做 / 进行中 / 卡住 / 已完成 / 已放弃 |
| 优先级 | select(单选) | 脚本 | 高 / 中 / 低，仅三档 |
| 所属项目 | text | 用户 | 项目名。当前为文本，非关联字段（见 4.1 缺口 1） |
| 父任务ID | text | 用户 | 子任务填父任务 ID；顶层任务留空 |
| 计划日 | datetime | 用户 | 打算哪天做。`list --today` 依据此字段 |
| 截止日 | datetime | 用户 | 硬性期限。超期由 `stats` 识别 |
| 预估分钟 | number | 用户 | 默认 25 |
| 实际分钟 | number | 用户 | 完成时填，用于校准估算偏差 |
| 顺延次数 | number | 脚本 | `block` 时 +1，**完成时不清零**，用于识别反复推迟 |
| 卡点 | text | 脚本 | 卡住原因原文，不做润色 |
| 进展 | text | 脚本 | 上次停手时做到哪。跨日任务的续命字段 |
| 小结 | text | 脚本 | 完成结论，或"放弃：原因" |
| 产出链接 | text | 用户 | 产出文档路径或链接 |
| 开始时间 | datetime | 脚本 | `start` 时写入 |
| 完成时间 | datetime | 脚本 | `done` / `drop` 时写入 |
| 归档月 | text | 脚本 | 形如 `2026-11`，标记该条已进入归档期 |
| 创建时间 | created_at | 飞书自动 | |
| 更新时间 | updated_at | 飞书自动 | |

### 3.3 状态机

```
                    ┌─────────┐
       add ────────►│  待做   │
                    └────┬────┘
                         │ start
                    ┌────▼────┐
                    │ 进行中  │◄──────┐
                    └────┬────┘       │ update --status doing
                         │ block      │
                    ┌────▼────┐       │
                    │  卡住   │───────┘
                    └────┬────┘
                         │
      done（须 --summary）│   drop（须 --reason）
                    ┌────▼────┐   ┌─────────┐
                    │ 已完成  │   │ 已放弃   │
                    └─────────┘   └─────────┘
                     终态，进入月度归档
```

- `done` 和 `dropped` 是终态，写入即打 `归档月` 标记
- 已终态的任务不再出现在活跃视图中
- **当前实现未做状态前置校验**（见 4.1 缺口 4）

### 3.4 命令清单

所有命令输出统一为 JSON：`{"ok": true/false, ...}`，失败时退出码非零。

| 命令 | 作用 | 强制校验 |
|---|---|---|
| `add <title>` | 新增任务 | 任务名不能为空 |
| `list [--status] [--project] [--parent] [--today] [--search]` | 列出任务 | — |
| `show <id>` | 单条详情，附子任务列表 | — |
| `start <id>` | 转进行中，写开始时间 | 任务必须存在 |
| `update <id> [--progress] [...]` | 改字段 | 至少改一项；status 必须是合法枚举 |
| `done <id> --summary "..."` | 转已完成，生成总结文档 | **`--summary` 必填** |
| `block <id> --reason "..."` | 转卡住，顺延 +1 | **`--reason` 必填** |
| `drop <id> --reason "..."` | 转已放弃 | **`--reason` 必填** |
| `stats` | 计数、项目分布、超期、反复顺延 | — |
| `doctor` | 环境自检 6 项 | — |
| `sync` | 重新生成派生视图 | — |
| `export` | 导出全量快照 | — |

**参数设计要点：**

- `--pri` 接受 `高/中/低`、`1/2/3`、`high/mid/low`，脚本归一后写入
- `--status` 接受 `todo/doing/blocked/done/dropped` 及对应中文，脚本做别名映射
- select 字段写入时必须包装成数组 `["进行中"]`。写字符串会失败——这是飞书 API 的约束，脚本内已统一处理
- 日期参数统一 `YYYY-MM-DD`，写入时转成当天 00:00 的毫秒时间戳

**校验失败时的报错要说明"为什么"**，而不只是"不允许"。例如完成不写结论时返回：

```
完成必须写一句结论（--summary）。这条规则是为了防止「假完成」：只发了个消息问别人不算完成。
```

### 3.5 读写路径

**读路径（所有命令的第一步都是它）**

```
read_all()  →  lark-cli base +record-list --format json
            →  一次调用返回全部记录（字段名数组 + 行数据数组 + record_id 数组）
            →  拼装成 dict，交给 simplify() 清洗
```

`simplify()` 负责三件事：select 数组解包取首元素、毫秒时间戳转 `YYYY-MM-DD HH:MM`、枚举值归一。任何下游逻辑只接触清洗后的字典，不直接碰飞书原始结构。

**写路径**

```
cmd_*  →  校验（必填项 / 枚举 / 任务存在性）
       →  create_record() 或 update_record()
       →  重新 read_all()   ← 关键：写后再读，确保归档反映的是服务端真实状态
       →  archive()         ← 派生三个产物
       →  输出 JSON
```

写后重读这一步不能省。飞书的字段计算（如 auto_number、updated_at）在写入响应里不一定完整，直接拿本地拼的数据归档会出现 ID 为空。

### 3.6 归档实现

`archive()` 一次执行生成三个产物：

**① `data/tasks.json`** — 机器可读全量快照·冷备

```json
{
  "snapshot_at": "2026-11-13 17:17:42",
  "base_token": "...", "table_id": "...", "base_url": "...",
  "count": 0,
  "tasks": []
}
```

带 `base_token` / `table_id` 是为了校验"这份快照是不是来自同一个库"。定位是**冷备与可 grep 的明文**，不是日常恢复手段（恢复见 3.7）。

**② `DASHBOARD.md`** — 看板（主要给 agent 与本地编辑器，飞书视图/仪表盘服务人）

| 区块 | 内容 | 排序逻辑 |
|---|---|---|
| 概览 | 五个状态的计数 | — |
| 进行中 | 任务 / 项目 / 优先级 / 计划日 / 进展 | 高优先级优先，再按计划日 |
| 卡住 | 任务 / 卡在哪 / 顺延次数 | 按原顺序，卡点原文不截断到不可读 |
| 待做 | 前 15 条 + 剩余条数 | 优先级，同优先级顺延多的在前 |
| 项目分布 | 未完成数 / 其中进行中 | 按未完成数降序 |
| 最近完成 | 完成时间 / 任务 / 结论 | 按完成时间降序，取 10 条 |

**③ `archive/YYYY-MM/ledger.md`** — 月度台账，只追加，进 git

把已完成/已放弃的任务追加成表格行。去重方式是**扫描已有台账提取任务 ID**，已入账的跳过。这样重复执行 `sync` 不会产生重复行。它是"总结"职责的书面形态：按月翻旧账、十年后可开、diff 可见变更历史。

### 3.7 恢复方式

前提：本机 WorkBuddy 的飞书连接器已授权。

```bash
# 1. 新机器上 clone 数据仓，再把工具仓内容放进数据仓根目录
# 2. 自检
python task.py doctor

# 3. doctor 报 lark-cli 找不到时，在 config.json 指定路径
# 4. 确认能读数据
python task.py list
```

**只要目录和飞书授权这两样在，环境就恢复了。** 不需要装数据库、不需要起服务、不需要 pip install（脚本纯标准库）。`data/tasks.json` 不在恢复路径上——它只在飞书库本身出问题（误删库、账号异常）时才作为冷备登场，此时用 `add` 逐条或脚本批量回灌即可。

`config.json` 只有 5 个键：`base_token`、`table_id`、`base_url`、`archive_dir`、`tz_offset_hours`。换库时改前两个即可，脚本不用动。

### 3.8 定时任务设计（当前已删除）

定时任务在本设计中承担"主动提醒"，但它与主库是**松耦合**的：每个任务只读写文件/表，彼此不直接通信，因此任何一个失败都不阻塞其他环节。

已设计过、当前已按需删除的四条：

| 时间 | 名称 | 职责 | 只读/可写 |
|---|---|---|---|
| 工作日 08:40 | 早上：今天该做什么 | `stats` + 按状态列表，给出今日三件和第一动作 | **只读，不改数据** |
| 工作日 每 2 小时 | 整点：现在该干什么 | 看进行中的任务，提示下一步；询问是否记录进展 | 可写（进展），**不改状态** |
| 工作日 21:30 | 晚上：结算今天 | 判定每件结局，补记录，commit | 可写 |
| 周五 18:00 | 周复盘 | 完成率、反复顺延、卡点分布、估算偏差 | 只读 + 写复盘文档 |

三条共同约束（写进提示词，防止 agent 越权）：

1. **不替使用者做决定**：不改截止日、不放弃任务、不新建任务
2. **不改状态**：只有使用者明确说"开始X""做完了"才改
3. **回复控制在 3–6 行**：要的是"现在做什么"，不是报告

飞书侧另有一条工作流「工作日早 8:30 推送今日安排」，**当前为 disabled**。它是独立于 WorkBuddy 的推送通道，跑在飞书服务器上，不依赖本机开机。

## 4. 现状与缺口

### 4.1 设计与实现的差距

诚实列出，避免把未做的当成已做的。

| # | 缺口 | 影响 | 优先级 |
|---|---|---|---|
| 1 | **项目层级未实现**。`所属项目` 是文本字段，没有独立项目表，无法表达"大项目含子项目" | 只能靠命名约定（如 `推理验收/指标口径`）模拟层级，无法算项目进度百分比 | 高 |
| 2 | **顺延无强制拦截**。只在 `stats` 中列出顺延 ≥2 的任务，不阻断操作 | "第三次顺延就介入"目前靠人看，不靠系统 | 中 |
| 3 | **脚本不自动提交 git**。`archive()` 只写文件，不 commit、不 push | 归档产物的变更历史为空；原设计的"执行完立刻 push"未实现 | 中 |
| 4 | **无状态机前置校验**。可以对待做任务直接 `done`，无需先 `start` | 数据上允许跳过"进行中"，统计会少一段 | 低 |
| 5 | `done` 不清空 `进展` 字段 | 已完成任务仍带旧进展文本，无害但冗余 | 低 |

### 4.3 优先级建议

**唯一真正的阻塞项是「0 条记录」。** 空系统跑起来比没有更糟——每天早上对着空表排计划，三天后使用者就会认为这东西没用。

因此下一步应该是：**先录 5–10 件手上真实在做的事**，跑一周，看 `stats` 和 `DASHBOARD.md` 的输出是否对得上实际感受。数据模型的问题只有在有数据之后才暴露得出来，现在继续加功能是在猜。

次优先级（有数据之后再做，各是半小时内的事）：

1. **飞书侧补「⑤ 已完成归档」视图**——按状态筛选已完成/已放弃，按归档月分组。这是"总结归档方便后续查阅"在飞书内的直接入口，手机上也能翻旧账。
2. **补状态机前置校验 + 顺延强制拦截**（4.1 缺口 2、4）——"第三次顺延就介入"从靠人看变成系统拦。

## 5. 验收标准

不是"功能都实现了"，而是三个月后能否满足：

| # | 状态 | 怎么验证 |
|---|---|---|
| 1 | 早上不用问任何人，就知道今天该做哪三件 | 打开飞书看「① 今日」视图或收到推送后，5 秒内能决定第一件事 |
| 2 | 能说出"这个月完成 12 件，卡点最多的是等客户回复" | `stats` 和月度台账能直接给出这个结论，不需要手工统计 |
| 3 | 任务第三次顺延时会被看见 | `stats` 的 `repeatedly_deferred` 里出现它，且排序让它排在前面 |
| 4 | 跨日任务重新开始时，不需要回忆上下文 | `update --progress` 里的那句话足够直接接续 |
| 5 | 想找三个月前某件事的结论，30 秒内能找到 | 飞书「⑤ 已完成归档」视图按月翻，或本地 `ledger.md` / `notes/` grep |
| 6 | 换一台机器，10 分钟内恢复可用 | `doctor` 全绿 + `list` 能返回数据 |

第 2、5 条对应"总结归档"职责，第 1、3、4 条对应"闭环"职责。其中第 3 条最容易失效——顺延的拦截与曝光如果失灵，任务会无声烂掉，那时剩下的功能加起来也不如一个记事本。

## 附录 A：为什么"一个任务一行"优于"一个任务一个文件"

以 40 个活跃任务为例：

| 方案 | 盘点一次的总读取次数 | 总行数 | 上下文占用 |
|---|---|---|---|
| 一个任务一个文件 | 40 次 `Read` | ≈1600 行 | 高，且随任务数线性增长 |
| 单表（飞书 / 单文件） | **1 次调用** | 40 行 | 低，且服务端可过滤 |

差距是 40 倍，而且随任务数增长而扩大。这不只是"快一点"的问题：**查询越贵，agent 越倾向于不查**，而一个不被查询的任务系统等于不存在。这是 I2 的由来。

## 附录 B：为什么不用日历做主库

| 能力 | 日历 | 多维表格 |
|---|---|---|
| 时间块视角 | ✅ 原生 | ✅ 日历视图 |
| 状态字段（待做/进行中/完成/放弃） | ❌ 无 | ✅ select |
| 优先级 | ❌ 无 | ✅ select |
| 按状态一次查出全部 | ❌ 无状态概念 | ✅ 服务端过滤 |
| 项目层级 | ❌ 无 | ✅ 文本/关联字段 |
| 归档 | ❌ 无 | ✅ 字段标记 + 视图过滤 |
| 统计 | ❌ 无 | ✅ 仪表盘 |

结论：日历是**时间块容器**，多维表格是**任务数据库**。前者只能回答"哪天有空"，后者才能回答"什么没做完"。用日历存任务，等于把状态塞进事件标题里，之后无法做任何统计。
